# Состав телеметрии

Время журналов 1С - местное время сервера, в OpenTelemetry оно передается в UTC
по часовому поясу из настройки `otel.v8-logs.timezone`.

## Ресурс

Данные журналов отправляются с отдельным ресурсом, не с ресурсом коллектора:

| Атрибут ресурса | Значение |
|-----------------|----------|
| `service.name` | `otel.v8-logs.service.name` или `service-name` источника |
| `v8.infobase.name` | информационная база: для журнала регистрации - `infobase` источника; для технологического журнала - свойство события `p:processName`, а если оно пустое - `infobase` источника |
| атрибуты из `otel.v8-logs.resource.attributes` | как заданы |
| `telemetry.sdk.name`, `telemetry.sdk.language`, `telemetry.sdk.version` | SDK, который отправил данные: `oscript-opentelemetry`, `oscript`, версия SDK |

Loki делает индексируемыми метками только атрибуты ресурса из своего списка (`service.name`
и другие, см. [документацию Loki](https://grafana.com/docs/loki/latest/send-data/otel/)), остальные
сохраняются как структурированные метаданные. Чтобы база стала меткой `v8_infobase_name`,
добавьте `v8.infobase.name` в `limits_config.otlp_config` Loki - пример в `demo/loki-config.yaml`.

В технологическом журнале `p:processName` бывает и не базой: в журнале файловой базы на macOS
(8.3.27) у событий отладчика оно равно `RemoteDebugger` и `DebugControlCenter`, и эти значения
тоже попадают в `v8.infobase.name`.

## Технологический журнал

### Логи

Каждое событие - запись лога (область инструментирования `opentelemetry-v8-logs.techlog`).

| Поле | Значение |
|------|----------|
| Время | время окончания события |
| Тело | исходный текст события; длиннее лимита - обрезается, см. [ограничение размеров](./telemetry.md#ограничение-размеров) |
| Серьезность | из свойства события `level`: `TRACE`, `DEBUG`, `INFO`, `WARNING` - `WARN`, `ERROR`; без него или при другом значении - по имени события: `ERROR` для `EXCP`; `WARN` для `ATTN`, `TDEADLOCK`, `TTIMEOUT`; иначе `INFO` |
| `v8.techlog.event.name` | имя события (`CALL`, `DBMSSQL`...) |
| `v8.techlog.duration` | длительность, мкс |
| `v8.techlog.depth` | уровень вложенности |
| `v8.techlog.<свойство>` | свойства события как есть: `v8.techlog.t:clientID`, `v8.techlog.Sql`...; повторяющиеся свойства - массивом. Свойства, значение которых целиком записано атрибутом семантических соглашений, не записываются: `Usr` (`user.name`), `t:computerName` (`client.address`), `SessionID` (`session.id`), `Context` (`code.stacktrace`), `Rows` (`db.response.returned_rows`), у `EXCP` - `Exception` и `Descr` (`exception.type`, `exception.stacktrace`). Без атрибута семантических соглашений (например, `session.id` выключен) свойство записывается. Настройка `otel.v8-logs.semconv-duplicates.skip.enabled` |
| `process.executable.name`, `process.pid` | процесс и PID из имени каталога или файла |
| `log.file.path`, `log.file.name` | путь к файлу журнала и имя файла |
| `user.name` | пользователь из свойства `Usr` |
| `client.address` | компьютер клиента из свойства `t:computerName`; у фоновых и регламентных заданий - сам сервер |
| `rpc.system.name`, `rpc.method` | у `CALL` и `SCALL` с `IName` и `MName`: `1c.v8` и `<IName>/<MName>`, например `IVResourceRemoteConnection/send`; своего значения `rpc.system.name` для 1С в семантических соглашениях нет |
| `error.type` | `_OTHER` у вызова, завершившегося исключением для клиента (свойство `RetExcp`): типа исключения в событии нет; у вызова, ответившего на HTTP-запрос кодом 5xx, - код ответа |
| `http.*`, `url.*`, `server.*`, `user_agent.original` | у вызова, обработавшего HTTP-запрос, см. [HTTP-запросы](./telemetry.md#http-запросы) |
| `v8.trace.detached_trace_id` | у вызова, продолжившего внешнюю трассу из заголовков запроса: прежняя трасса, в которой остались спаны, отправленные до запроса, см. [HTTP-запросы](./telemetry.md#http-запросы) |
| `session.id` | номер сеанса из свойства `SessionID`; настройка `otel.v8-logs.session-id.enabled` |
| `db.system.name`, `db.namespace`, `server.address` | у событий СУБД, см. [трассы](./telemetry.md#трассы) |
| `db.response.returned_rows` | у событий СУБД, настройка `otel.v8-logs.returned-rows.enabled`: число строк результата из свойства `Rows`. Платформа пишет `Rows` только у запросов, которые возвращают строки; у изменяющих запросов его нет, число изменённых строк - в `RowsAffected` |
| `code.stacktrace`, `code.file.path`, `code.line.number`, `code.function.name` | место в коде из свойства `Context`, см. [место в коде](./telemetry.md#место-в-коде) |
| `v8.techlog.truncation.attributes` | ключи обрезанных атрибутов, массив строк; без обрезки атрибута нет |
| `v8.techlog.truncation.body.original_size` | размер тела до обрезки, байт; только у записи лога с обрезанным телом |
| `v8.techlog.truncation.body.attributes` | имена свойств, значения которых обрезаны в теле, массив строк по порядку текста события; только у записи лога, тело которой обрезано внутри значений |

Секреты в `Headers`, `URI` и `url.query` в атрибуты и в тело записи не попадают. Значение
заголовка `Authorization`, `Cookie`, `Set-Cookie`, `Proxy-Authorization` и заголовка, в имени которого
есть `Token`, `Api-Key` или `Secret`, заменяется на `***`, вместе со строками продолжения этого
заголовка. То же с именем из настройки `otel.v8-logs.secret-headers`: оно сравнивается целиком.
То же со значением параметра `access_token`, `token`, `password` и `sig`
в `URI`, `url.query` и в строке запроса внутри значения любого заголовка, в том числе
`1C-OriginalLocation`, `1C-BaseLocation`, `Referer` и `Location`: имя сравнивается после
раскодирования URL (`access%5Ftoken` - то же, что `access_token`), в журнал пишется исходное
написание имени. В `1C-ConnectString` скрываются `Pwd`, `DBPwd` и `SPwd`.

Запись лога и спан события получают один набор атрибутов: атрибуты раскладываются один раз на событие.
Отличаются только атрибуты исключения - они у записи лога `EXCP`, а в спане - у события спана `exception`, -
и атрибуты обрезки тела: тело есть только у записи лога.

#### Исключения

Исключение `EXCP` записывается событием по семантическим соглашениям
[exceptions-logs](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-logs/):

| Поле | Значение |
|------|----------|
| Имя события | `exception` |
| `exception.type` | свойство `Exception`; без свойства атрибута нет |
| `exception.message` | текст первого уровня цепочки ошибок из свойства `Descr`; без свойства атрибута нет |
| `exception.stacktrace` | свойство `Descr` целиком; без свойства атрибута нет |

Свойство `Descr` - цепочка ошибок платформы. Уровень цепочки начинается строкой «`<GUID>: текст`»,
перед уровнями и после них бывают места в коде платформы (`src\rserver\src\RMngrCalls.cpp(536):`,
`File=src\rserver\src\IRMngrSrvcImpl.cpp(639)`), между уровнями - кадры встроенного языка
(`{ОбщийМодуль.Имя.Модуль(147)}: выражение`):

```
src\rserver\src\ServerJobExecutor.cpp(1365):
8d366056-4d5a-4d88-a207-0ae535b7d28e: Ошибка при вызове метода контекста (ВызватьHTTPМетод)
{ОбщийМодуль.пэмМетрикиСервер.Модуль(147)}:	Результат = HTTPСоединение.ВызватьHTTPМетод("POST", HTTPЗапрос);
f08d92f8-9eb2-4e19-9dd9-977d907cec2d
896db6ac-cc39-4065-8298-1bf5fccb9d98: Ошибка работы с Интернет: Couldn't resolve host name
```

`exception.message` - текст после первого «`<GUID>: `» (если такой строки нет - от начала `Descr`)
до первой из границ: строки следующего уровня (`<GUID>` или «`<GUID>: `»), кадра встроенного языка
(`{...(N)}:`), строки, начинающейся с `ID=` или `File=`, места в коде платформы
(`: src/core/src/Storage64.cpp(3220)`). Текст может быть многострочным. В примере выше
`exception.message` - «Ошибка при вызове метода контекста (ВызватьHTTPМетод)», `exception.stacktrace` -
весь `Descr`. Если текст до первой границы пустой (`Descr` начинается с кадра встроенного языка),
`exception.message` - весь `Descr`.

#### Место в коде

Свойство `Context` - стек вызовов встроенного языка. Первая строка - внешний кадр, каждая следующая
вызвана из предыдущей, последняя - место, где выполнялся код в момент события:

```
РегистрСведений.Состояния.МодульМенеджера : 414 : Т = ТаблицаСостояний(Заказы);
	РегистрСведений.Состояния.МодульМенеджера : 630 : Т = Запрос.Выполнить().Выгрузить();
```

Кадр - строка `Модуль : НомерСтроки : Выражение`, где выражение - текст этой строки модуля.
У модуля расширения перед модулем стоит имя расширения: `тцрОбмен ОбщийМодуль.ТЦР_Сервер.Модуль`.
У динамического кода (`Выполнить`, `Вычислить`) модуль пустой: ` : 13 : Выборка = Запрос.Выполнить();`.
Вызов сервера записывается строкой `ОбщийМодуль.Вызов : <модуль>.<метод>` или
`Форма.Вызов : <форма>.Модуль.<метод>`; модуль формы в кадрах называется `<форма>.Форма`.
Метод вызова сервера должен быть идентификатором: внутренние вызовы платформы
(`...Модуль.form::forceLockProperties`, `...Модуль.item::Список::saveCurrentSelectedSettings`) вызовом
функции модуля не считаются.

В английском варианте встроенного языка формат тот же, имена - английские:

| Русский вариант | Английский вариант |
|-----------------|--------------------|
| `ОбщийМодуль.ОбщийСервер.Модуль : 4 : ...` | `CommonModule.CommonServer.Module : 4 : ...` |
| `Документ.Документ.МодульОбъекта : 23 : ...` | `Document.Document.ObjectModule : 23 : ...` |
| `Документ.Документ.МодульМенеджера : 4 : ...` | `Document.Document.ManagerModule : 4 : ...` |
| `ОбщийМодуль.Вызов : ОбщийМодуль.ОбщийСервер.Модуль.Количество` | `CommonModule.Call : CommonModule.CommonServer.Module.Count` |
| `Форма.Вызов : Документ.Документ.Форма.ФормаОбъекта.Модуль.КоличествоНаСервере`, кадр `...ФормаОбъекта.Форма` | `Form.Call : Document.Document.Form.ObjectForm.Module.ServerCount`, кадр `...ObjectForm.Form` |
| `{ОбщийМодуль.ОбщийСервер.Модуль(8)}:` в `Descr` | `{CommonModule.CommonServer.Module(8)}:` в `Descr` |

| Атрибут | Значение |
|---------|----------|
| `code.stacktrace` | свойство `Context` как есть |
| `code.file.path` | модуль последнего кадра; у вызова сервера без кадров - модуль вызова |
| `code.line.number` | номер строки последнего кадра |
| `code.function.name` | `<модуль>.<функция>`, только если функцию можно определить надежно (см. ниже) |

Если последний кадр - динамический код, его номер строки относится к тексту, переданному в
`Выполнить` или `Вычислить`, а не к модулю. Место в коде тогда - ближайший кадр выше с модулем,
то есть строка, выполнившая этот текст. Если в `Context` нет ни кадра с модулем, ни вызова сервера
(`Форма.Записать : Документ.Заказ.Форма.ФормаДокумента`, `Система.ПолучитьФорму : ...`), есть только
`code.stacktrace`. У `EXCP` без `Context` модуль и строка берутся из первого кадра
`{Модуль(строка)}` свойства `Descr`, `code.stacktrace` нет.

В кадре нет имени функции, в которой лежит его строка: выражение `Т = Запрос.Выполнить().Выгрузить();`
показывает, что вызывается из строки 630, а не какой функции она принадлежит. Функция определяется по
предыдущей строке `Context` - месту, откуда она вызвана, и только в одном из случаев:

| Предыдущая строка | Пример | `code.function.name` |
|-------------------|--------|----------------------|
| вызов сервера этого модуля | `ОбщийМодуль.Вызов : ОбщийМодуль.ДлительныеОперации.Модуль.ФоновоеЗаданиеЗавершено` | `ОбщийМодуль.ДлительныеОперации.Модуль.ФоновоеЗаданиеЗавершено` |
| кадр того же модуля с вызовом без квалификатора | `... : 414 : Т = ТаблицаСостояний(Заказы);` | `РегистрСведений.Состояния.МодульМенеджера.ТаблицаСостояний` |
| вызов функции общего модуля последнего кадра | `... : 6389 : Если Не ОбщегоНазначения.СсылкаСуществует(Ключ) Тогда` | `ОбщийМодуль.ОбщегоНазначения.Модуль.СсылкаСуществует` |
| вызов функции модуля менеджера последнего кадра | `... : 101 : РегистрыСведений.Состояния.ОтразитьСостояние(Заказы);` | `РегистрСведений.Состояния.МодульМенеджера.ОтразитьСостояние` |

В кадре должен быть законченный оператор с единственным вызовом:

- скобки закрыты, оператор завершен `;`, а `Если`, `ИначеЕсли`, `Пока`, `Для` - словами `Тогда` и `Цикл`;
  строка не начинается с `И`, `ИЛИ`, `НЕ`. В кадре одна строка модуля, и у многострочного оператора
  выполняемый вызов может быть на другой строке: `Если ПолучитьФункциональнуюОпцию("...")` с
  продолжением `И ЭтотТипДолженПроверяться(...) Тогда` функцию не определяет;
- вызов один: `ЗначенияРеквизитов(ЗначениеВМассиве(Ссылка))` и цепочки `Запрос.Выполнить().Выбрать()`
  функцию не определяют. Содержимое строк и комментарий не учитываются, `Новый Массив(...)` - не вызов;
- вызов не метод платформы, который передает управление обработчику события модуля: `Записать`,
  `Прочитать`, `Удалить`, `УстановитьПометкуУдаления`, `ПроверитьЗаполнение`, `Заполнить`, `Скопировать`,
  `ПолучитьФорму`, `ПолучитьДанныеВыбора`, `Загрузить`, `Сохранить`, `ПолучитьОписание`,
  `УстановитьОписание`. Так, `Записать()` в модуле объекта вызывает его `ПередЗаписью`;
- вызов без квалификатора не глобальный метод, который вызывает процедуры модуля: `ВыполнитьОбработкуОповещения`,
  `Оповестить`, `ОповеститьОВыборе`, `ОткрытьФорму`, `ОткрытьФормуМодально`. Так,
  `ВыполнитьОбработкуОповещения(Оповещение, Результат)` вызывает обработчик оповещения того же модуля формы.
  Через квалификатор (`СерверныеОповещения.Оповестить(...)`) вызывается функция общего модуля, и она определяется;
- вызов через переменную (`Объект.ПроверитьЗаполнение()`, `МодульСервиса.Функция()`) функцию не
  определяет: по тексту не видно, какой модуль вызывается.

Квалификатор сопоставляется с модулем последнего кадра без имени расширения в обоих вариантах
встроенного языка: `ОбменДанными` - `ОбщийМодуль.ОбменДанными.Модуль` или `CommonModule.ОбменДанными.Module`,
`Документы.Заказ` и `Documents.Заказ` - `Документ.Заказ.МодульМенеджера` или `Document.Заказ.ManagerModule`
Менеджеры с модулем менеджера:

| Коллекция | Вид объекта в кадре |
|-----------|---------------------|
| `Справочники`, `Catalogs` | `Справочник`, `Catalog` |
| `Документы`, `Documents` | `Документ`, `Document` |
| `ЖурналыДокументов`, `DocumentJournals` | `ЖурналДокументов`, `DocumentJournal` |
| `Перечисления`, `Enums` | `Перечисление`, `Enum` |
| `Отчеты`, `Reports` | `Отчет`, `Report` |
| `Обработки`, `DataProcessors` | `Обработка`, `DataProcessor` |
| `ПланыВидовХарактеристик`, `ChartsOfCharacteristicTypes` | `ПланВидовХарактеристик`, `ChartOfCharacteristicTypes` |
| `ПланыСчетов`, `ChartsOfAccounts` | `ПланСчетов`, `ChartOfAccounts` |
| `ПланыВидовРасчета`, `ChartsOfCalculationTypes` | `ПланВидовРасчета`, `ChartOfCalculationTypes` |
| `ПланыОбмена`, `ExchangePlans` | `ПланОбмена`, `ExchangePlan` |
| `РегистрыСведений`, `InformationRegisters` | `РегистрСведений`, `InformationRegister` |
| `РегистрыНакопления`, `AccumulationRegisters` | `РегистрНакопления`, `AccumulationRegister` |
| `РегистрыБухгалтерии`, `AccountingRegisters` | `РегистрБухгалтерии`, `AccountingRegister` |
| `РегистрыРасчета`, `CalculationRegisters` | `РегистрРасчета`, `CalculationRegister` |
| `БизнесПроцессы`, `BusinessProcesses` | `БизнесПроцесс`, `BusinessProcess` |
| `Задачи`, `Tasks` | `Задача`, `Task` |
| `ХранилищаНастроек`, `SettingsStorages` | `ХранилищеНастроек`, `SettingsStorage` |
| `Константы`, `Constants` | `Константа`, `Constant` |
| `КритерииОтбора`, `FilterCriteria` | `КритерийОтбора`, `FilterCriterion` |

Модули набора записей, менеджера значения константы и команд через квалификатор не вызываются: функция
в них определяется по вызову без квалификатора в том же модуле.

#### Ограничение размеров

Тело записи лога и значения атрибутов ограничены по размеру в байтах UTF-8:

| Что | Лимит по умолчанию | Настройка |
|-----|--------------------|-----------|
| тело записи лога | 131 072 (128 КБ) | `otel.v8-logs.limits.body-size` |
| строковое значение атрибута записи лога, спана и события спана; у массива и соответствия - каждая строка на любой глубине | 2 048 | `otel.v8-logs.limits.attribute-value-size` |
| сумма ключей и значений атрибутов записи лога; у технологического журнала тот же набор атрибутов получают спан и событие спана `exception` | 32 768 (32 КБ) | `otel.v8-logs.limits.attributes-size` |

Значение длиннее лимита обрезается по границе символа, в конце ставится метка `...[truncated]`;
метка входит в лимит, а в лимит меньше 15 байт значение обрезается без метки. Отрицательный лимит,
как и `0`, - без ограничения. Когда сумма атрибутов превышает лимит, сначала обрезается самая длинная
строка, в том числе внутри массива или соответствия (например, в `v8.eventlog.data`). Обрезанные ключи перечисляются в `v8.techlog.truncation.attributes`, размер
тела до обрезки - в `v8.techlog.truncation.body.original_size`.

Полный текст события остается в теле записи лога, пока он короче лимита тела: длинные свойства
(`Sql`, `Sdbl`, `Locks`, `Context` в `code.stacktrace`) обрезаются в атрибутах до 2 КБ, но в теле - до 128 КБ.

Тело длиннее лимита обрезается внутри значений свойств, у журнала регистрации - внутри полей записи:
сначала самое длинное значение, пока тело не поместится в лимит. Имена свойств, кавычки, разделители
и остальные значения остаются целиком, каждое обрезанное значение - не короче одного символа с меткой
`...[truncated]`, метка - внутри кавычек значения:
`05:12.000001-15,SDBL,1,...,Sdbl='SELECT ...[truncated]',Rows=1,Context='Форма.Вызов : ...'`. Обрезка
не разрывает удвоенную кавычку текстового формата и escape-последовательность формата JSON. Обрезанные
свойства и поля перечисляются в `v8.techlog.truncation.body.attributes` и
`v8.eventlog.truncation.body.attributes`. Если тело не помещается в лимит и с обрезанными значениями,
обрезается его конец, а списка обрезанных значений нет.

Лимиты по умолчанию проверены на стеке из `demo` (`grafana/otel-lgtm`) на технологическом журнале
с событиями до 70 МБ и на журнале регистрации с комментариями до 40 МБ, представлением данных и
данными по 50 000 символов: запись проходит ограничения Loki на строку (256 КБ) и на structured metadata
(64 КБ на сумму атрибутов записи), значения атрибутов не превышают 2 КБ, после которых Tempo
обрезает их без метки, запросы экспорта остаются в пределах приема OpenTelemetry Collector
(20 МБ), трассы - в пределах Tempo (5 МБ), а ответы Loki на запрос 1000 строк в Grafana - в пределах
4 МБ.

### Метрики

| Метрика | Тип | Атрибуты |
|---------|-----|----------|
| `v8.techlog.event.duration`, с | гистограмма | `v8.techlog.event.name`, `process.executable.name`, `v8.infobase.name` |
| `v8.techlog.truncated`, `{value}` | счетчик | `v8.techlog.event.name`, `v8.infobase.name`, `v8.techlog.truncation.target`, `v8.techlog.truncation.attribute` |
| `v8.techlog.truncated.size`, `By` | счетчик | те же |
| `db.client.operation.duration`, с | гистограмма | `db.system.name`, `db.namespace`, `server.address` |
| `rpc.server.call.duration`, с | гистограмма | `rpc.system.name`, `rpc.method`, `error.type` |
| `rpc.client.call.duration`, с | гистограмма | `rpc.system.name`, `rpc.method`, `error.type` |
| `http.server.request.duration`, с | гистограмма | `http.request.method`, `url.scheme`, `http.response.status_code`, `http.route`, `error.type` |

`v8.techlog.truncated` - число обрезанных значений, `v8.techlog.truncated.size` - отрезанные байты,
см. [ограничение размеров](./telemetry.md#ограничение-размеров). `v8.techlog.truncation.target` - `body`
(тело записи лога) или `attribute` (значение атрибута, его ключ - в `v8.techlog.truncation.attribute`).

`db.client.operation.duration` - метрика семантических соглашений: длительность событий СУБД
(`DBMSSQL`, `DBPOSTGRS`, `DBORACLE`, `DB2`, `DBV8DBEng`) с границами бакетов из семантических
соглашений. Атрибуты - те же, что у записи лога и спана события, см. [трассы](./telemetry.md#трассы).

`rpc.server.call.duration` и `rpc.client.call.duration` - метрики семантических соглашений RPC
(статус release candidate): длительность входящих (`CALL`) и исходящих (`SCALL`) вызовов метода
интерфейса платформы, то есть событий с `IName` и `MName`, с границами бакетов из семантических соглашений.

`http.server.request.duration` - метрика семантических соглашений HTTP: длительность вызова (`CALL`),
обработавшего HTTP-запрос, то есть длительность HTTP-спана, см. [HTTP-запросы](./telemetry.md#http-запросы).
Границы бакетов - из семантических соглашений. `server.address` и `server.port` в метрику не попадают:
они берутся из заголовка `Host`, и по семантическим соглашениям их включают только по выбору из-за кардинальности.

### Трассы

Трасса - верхнеуровневое событие потока выполнения (процесс, `OSThread` и `t:clientID`, если он
есть) со всеми событиями, вложенными в него по уровню и времени. Платформа пишет событие
по окончании, поэтому вложенные события появляются в журнале раньше родителя. Сборщик исходит
из того, что события одного уровня в одном потоке по времени не пересекаются, и тогда охват
интервала `[окончание - длительность, окончание]` событием меньшего уровня означает, что событие -
предок. В журналах автономного сервера `ibsrv` и файловой базы (macOS, 8.3.27) это выполняется.

Трассы собираются в одном из двух режимов (настройка `otel.v8-logs.traces.mode`).

**Потоковый** (`streaming`). Спан каждого события отправляется сразу при чтении. Корень трассы -
событие вызова (`CALL`, настройка `otel.v8-logs.traces.root-events`) или событие уровня 0:
ниже уровня 0 стека нет, и предка у такого события быть не может. Идентификатор родителя
выдается заранее: событие уровня `d` ссылается на «слот» уровня `d-1`, а слот копит объединение
интервалов своих потомков. Событие уровня `d-1` занимает слот, только если его интервал охватывает
всех потомков слота. Если уровень не пишется в журнал или следующее событие этого уровня
не охватывает потомков, слот отправляется синтетическим спаном `UNLOGGED` с атрибутом
`v8.techlog.synthetic`. Корень закрывает трассу потока; ожидавшие события, которые он
не охватывает, закрываются отдельной трассой с синтетическим корнем. Трасса, в потоке которой больше
часа не было событий, закрывается синтетическим корнем.

В журнале `ibsrv` код пользователя - например, запись документа - выполняется внутри
`CALL,0` (`ib::worker::IInfoBaseWorkingContextCall.execute`) того же потока, без `t:clientID`
у вызова и его событий.

**Накопление** (`buffered`). В журнале файловой базы код пользователя выполняется в процессе клиента
(`1cv8c`, `1cv8`) без событий `CALL`, и верхнеуровневое событие становится известно, только когда
записан его предок или стало ясно, что предка не будет. События потока копятся в памяти деревьями
и отправляются: когда в потоке записано событие уровня 0 (охватить накопленные события после него
не может ничто), после минуты без событий потока (по времени журнала, а после прохода, дочитавшего
журналы, - по часам), при накоплении 10000 событий потока и при завершении работы. Каждое
верхнеуровневое событие - например, `SDBL Func=HoldConnection` с транзакцией внутри или отдельный
запрос - становится отдельной трассой. Записи лога отправляются сразу и со спаном не связаны:
спан и его запись лога находятся по `log.file.path` и времени.

Режим по умолчанию `auto`: накопление для процессов `1cv8` и `1cv8c`, потоковый для остальных.
Так выбрано по наблюдению: клиент, подключенный к серверу, событий `SDBL` не пишет, а клиент файловой
базы пишет. Режим можно задать явно для всех журналов или для источника (`traces-mode`).

#### Имена спанов

Имя спана состоит из имени события, операции и места вызова из последней непустой строки
собственного `Context`. Кадр `Модуль : строка : выражение` сокращается до `Модуль:строка`,
кадр без модуля — до `<dynamic>:строка`. Другой формат контекста сохраняется как текст.
Контекст дочернего события не заменяет имя родительского вызова.

| Событие | Имя | Пример |
|---------|-----|--------|
| `CALL`, обработавший HTTP-запрос | метод и маршрут `http.route`, неизвестный метод - `HTTP`, см. [HTTP-запросы](./telemetry.md#http-запросы) | `GET /erp/hs/dt/download/{ID}` |
| `CALL` фонового задания | `Module.Method`, если `Func=Background job` и оба поля заполнены | `CALL Jobs.Run` |
| `CALL` с собственным `Context` | место вызова | `CALL ОбщийМодуль.Обмен.Модуль:42` |
| `CALL`, `SCALL` | интерфейс и метод (`IName`, `MName` или `Method`), иначе `Func` | `SCALL ILogMngrData.writeLogEntryData`, `CALL Dynamic list search` |
| `CALL`, `SCALL` без метода и контекста | `Func` и, если доступны, `Form.FormItem` | `CALL Dynamic list search · Документ.Заказ.Форма.ФормаДокумента.Список` |
| `SDBL` | `Func`, иначе вид запроса и таблица | `SDBL HoldConnection`, `SDBL UPDATE Document54` |
| `DBMSSQL`, `DBPOSTGRS`, `DBORACLE`, `DB2`, `DBV8DBEng` | вид запроса и таблица; для ODBC `{call ...}` — `EXEC` и имя процедуры; без запроса — `Func` | `DBMSSQL INSERT _Document54`, `DBMSSQL EXEC sp_executesql`, `DBV8DBEng readFile` |
| `TLOCK` | пространства блокировок (`Regions`) | `TLOCK Document54.REFLOCK` |
| `EXCP` | тип исключения и место вызова; без `Context` — первый кадр `{Модуль(строка)}` из `Descr` | `EXCP RuntimeException · ОбщийМодуль.Test.Модуль:42` |
| синтетический | `UNLOGGED` | |

У событий, кроме `CALL` с собственным контекстом и фоновых заданий, место вызова добавляется
после операции через ` · `: `DBMSSQL SELECT _Document54 · ОбщийМодуль.Test.Модуль:42`.
Операция ограничена 100 символами, модуль — 120 (сохраняется конец имени и номер строки),
контекст неизвестного формата — 160. Исходные свойства остаются в атрибутах события.
Значения SQL-параметров в имя из запроса не включаются.

Правила именования одинаковы для `streaming`, `buffered` и `auto`. В потоковом режиме
спан отправляется сразу: отдельное событие `Context`, записанное после вызова, не меняет
его имя. Для этих правил нужен `Context` в свойствах самого события.

| Событие | Спан |
|---------|------|
| `CALL` | вид `SERVER`; с `IName` и `MName` - `rpc.system.name` и `rpc.method`; с `RetExcp` - статус `ERROR` с описанием из `RetExcp` и `error.type`; обработавший HTTP-запрос - атрибуты HTTP-сервера и статус `ERROR` при ответе 5xx |
| `SCALL` | вид `CLIENT`; с `IName` и `MName` - `rpc.system.name` и `rpc.method` |
| `DBMSSQL`, `DBPOSTGRS`, `DBORACLE`, `DB2`, `DBV8DBEng` | вид `CLIENT`, `db.system.name`, `db.namespace`, `server.address`, `db.response.returned_rows`; у файловой базы (`DBV8DBEng`) своего значения `db.system.name` в семантических соглашениях нет, используется `1c.v8dbeng` |
| `EXCP` | вид `INTERNAL`, статус `ERROR` с описанием из `Descr`, событие спана `exception` |
| остальные | вид `INTERNAL` |

`db.namespace` и `server.address` берутся из свойства `DataBase` в формате `<сервер>\<база>` - базы,
указанной при подключении; разделитель - последний `\`. У SQL Server с именованным экземпляром
(`<сервер>\<экземпляр>\<база>`) экземпляр входит в `db.namespace`: `server.address` = `<сервер>`,
`db.namespace` = `<экземпляр>|<база>`. Порт из сервера не выделяется. У файловой базы `DataBase` -
только имя базы, `server.address` нет. Без свойства `DataBase` атрибутов нет. У PostgreSQL
`db.namespace` - база без схемы: схемы в журнале нет. У Oracle база 1С - схема данных, а сервер базы
данных - TNS-имя, поэтому `server.address` - TNS-имя, а `db.namespace` не заполняется: по семантическим
соглашениям это уникальный идентификатор базы Oracle (`DB_UNIQUE_NAME`), которого в журнале нет.

Событие спана `exception` появляется в спане по-разному в зависимости от режима:

- в потоковом режиме его переносит из записи лога `EXCP` процессор событий в события спана SDK
  (`EventToSpanEventBridge`, включен по умолчанию, настройка `otel.oscript.event.to.span.event.bridge.enabled`).
  Запись лога пишется, пока спан события открыт, и атрибуты события спана - атрибуты записи лога.
  С выключенным процессором события `exception` в спане нет;
- в режиме накопления запись лога со спаном не связана, и событие добавляет сборщик трасс:
  `exception.type`, `exception.message` и `exception.stacktrace`, как у записи лога.

Атрибуты спанов - те же, что у записей лога. В потоковом режиме каждая запись лога события содержит
`trace_id` и `span_id` спана этого события: из Loki можно перейти в трассу в Tempo и обратно.

Состояние трасс хранится в памяти. Если приложение перезапустится посреди вызова, в потоковом режиме
вложенные события, отправленные до перезапуска, сошлются на родителя, который не придет; в режиме
накопления при аварийном завершении накопленные спаны теряются (при штатном - отправляются).

Для трасс в журнал нужно писать свойство `OSThread`, а для места вызова в именах спанов — `Context`.

Время спана - время события в журнале. Tempo записывает в метаданные блока время поступления данных,
если время спанов отстоит от него больше, чем на `ingestion_time_range_slack` (по умолчанию 2 минуты),
а поиск по интервалу времени выбирает блоки по метаданным. Поэтому спаны, выгруженные при первом
запуске по накопленным журналам или при догоне после простоя, с настройками Tempo по умолчанию
поиском по своему времени не находятся; по идентификатору трассы, в том числе из записи лога в Loki,
они открываются. В `demo/tempo-config.yaml` запас увеличен до срока хранения блоков (`336h`)
в разделах `storage.trace.wal`, `live_store.wal` и `block_builder.wal` (Tempo 3).

#### HTTP-запросы

HTTP-запрос к публикации (HTTP- и веб-сервисы, OData, тонкий и веб-клиент) журнал пишет парой событий
`VRSREQUEST` и `VRSRESPONSE`. В rphost за веб-сервером и в `ibsrv` пара записана внутри вызова
`CALL` того же потока уровнем выше: этот вызов получает атрибуты HTTP-сервера по семантическим
соглашениям и имя `{метод} {маршрут}`. События пары остаются своими спанами и записями лога.
Пара без охватывающего вызова (журнал веб-сервера, файловая публикация) остается только событиями VRS.

| Атрибут | Значение |
|---------|----------|
| `http.request.method` | метод запроса; не из списка семантических соглашений - `_OTHER`, исходный - в `http.request.method_original` |
| `url.path`, `url.query` | путь и параметры из `URI` (секреты скрыты) |
| `url.scheme` | схема из заголовка `1C-OriginalLocation` |
| `server.address`, `server.port` | из заголовка `Host` |
| `client.address` | первый адрес заголовка `X-Forwarded-For` - исходный клиент, а не веб-сервер из `t:computerName` |
| `user_agent.original` | заголовок `User-Agent` |
| `http.response.status_code` | `Status` из `VRSRESPONSE` |
| `error.type` | код ответа 5xx; спан получает статус `ERROR`. Ответ 4xx ошибкой HTTP-сервера не считается |
| `http.route` | маршрут низкой кардинальности, ниже |

Шаблона маршрута, который выбрала платформа, в журнале нет, поэтому маршрут `http.route`
восстанавливается по адресу и заголовкам запроса: путь публикации из заголовка `1C-BaseLocation`
и маршрут внутри нее. Как и маппинг сервлета в инструментациях Java (`/path/*`), маршрут может быть
грубее шаблона метода: точнее всего он у HTTP-сервисов с шаблонами из настройки
`otel.v8-logs.http.routes`. Шаблоны настройки должны совпадать с шаблонами URL в конфигурации базы.

| Адрес | Маршрут | Пример |
|-------|---------|--------|
| `/hs/...` | шаблон из настройки `otel.v8-logs.http.routes`, без совпадения - `/hs/{корень}/*` | `/erp/hs/dt/download/{ID}`, `/erp/hs/mini/*` |
| `/ws/...` | путь описания из `1C-OriginalLocation` (IIS передает в `URI` адрес, который прислал клиент) и операция из заголовка `SOAPAction` | `/vrsfile/ws/ping.1cws/Ping` |
| `/odata/...` | имя сущности без ключа и дальнейшего пути | `/demo/odata/standard.odata/Catalog_Номенклатура` |
| `/e1cib/...` | не больше двух сегментов после `e1cib` | `/vrsmin/e1cib/cmi/commands` |
| `/e1csys/...` | статика клиента: группа ресурсов платформы без имени файла | `/vrsmin/e1csys/basic/*` |
| прочие | | `/vrsmin/*` |

Длительность такого вызова попадает в метрику `http.server.request.duration`. У вызова остаются и атрибуты
`rpc.system.name` и `rpc.method`, и метрика `rpc.server.call.duration`.

Если в заголовках `VRSREQUEST` есть контекст вызывающей стороны (веб-сервер передает заголовки
клиента без изменений), трасса вызова продолжает внешнюю: ее спаны получают внешний `trace_id`,
а корень трассы - вызов - становится потомком спана вызывающей стороны. Заголовки разбирают
пропагаторы SDK из настройки `otel.propagators` (`OTEL_PROPAGATORS`): по умолчанию `tracecontext,baggage`,
то есть заголовок `traceparent` (W3C Trace Context); `b3` и `b3multi` (пакет opentelemetry-propagator-b3)
разбирают заголовки B3, `none` отключает продолжение внешней трассы. Неверный заголовок пропускается.
В потоковом режиме спаны, записанные в вызове раньше `VRSREQUEST` (например, `SCALL` поиска рабочего
процесса `IClusterState.getWorkProcess`), к этому моменту уже отправлены и остаются в прежней трассе.
Корень ссылается на первый из них ссылкой (span link) и на прежнюю трассу - атрибутом
`v8.trace.detached_trace_id`, который есть и у записи лога вызова. В режиме накопления дерево вызова отправляется целиком, и внешнюю трассу
продолжают все его спаны.

## Журнал регистрации

### Логи

Каждая запись - запись лога (область инструментирования `opentelemetry-v8-logs.eventlog`).
Пустые поля не передаются.

| Поле | Значение |
|------|----------|
| Время | время записи |
| Тело | строка как в просмотре журнала, части через ` \| `: представление события (`v8.eventlog.event.presentation`); у событий с объектом метаданных или данными - объект, представление данных (без него - данные) и пользователь, у остальных - приложение, пользователь и `session=<номер>`, значения как в журнале. Пустые части пропускаются, комментарий - с новой строки. Например, `Данные. Проведение \| Document.Document \| Document 000000001 dated 10/20/2026 12:56:10 PM`, `Сеанс. Начало \| 1CV8C \| session=2`. Длиннее лимита - обрезается, см. [ограничение размеров](./telemetry.md#ограничение-размеров) |
| Серьезность | `E` - `ERROR`, `W` - `WARN`, `I` - `INFO`, `N` (примечание) - `DEBUG` |
| `v8.eventlog.event` | идентификатор события (`_$Session$_.Start`, `_$Data$_.Post`...) |
| `v8.eventlog.event.presentation` | представление события, как в просмотре журнала, на языке из настройки `otel.v8-logs.language`: «Данные. Проведение» или «Data. Posting». У событий без представления (события пользователя, события, которых нет в платформе 8.3.27) - идентификатор события, поэтому атрибут заполнен у всех записей |
| `user.name`, `user.id` | имя и идентификатор пользователя |
| `v8.eventlog.application` | приложение |
| `client.address` | компьютер записи |
| `v8.eventlog.computer` | компьютер записи, то же значение, что `client.address`; только при выключенной настройке `otel.v8-logs.semconv-duplicates.skip.enabled` |
| `v8.eventlog.connection` | соединение |
| `v8.eventlog.session` | сеанс; при включенной настройке `otel.v8-logs.semconv-duplicates.skip.enabled` - только когда `session.id` не записан |
| `session.id` | номер сеанса; настройка `otel.v8-logs.session-id.enabled` |
| `v8.eventlog.transaction.status` | `committed` (код `C`), `rolled_back` (код `R`): в журналах с этими кодами записаны события `_$Transaction$_.Commit` и `Rollback` |
| `v8.eventlog.transaction.status_code` | код статуса транзакции как есть: `C`, `R`, `U` (у изменений данных внутри транзакции; значение не расшифровывается) |
| `v8.eventlog.transaction.id` | номер транзакции |
| `v8.eventlog.metadata`, `v8.eventlog.metadata.uuid` | объект метаданных |
| `v8.eventlog.data` | Структурированный OTLP-атрибут с полями известной формы `Data`; для неизвестной формы — строка JSON с исходным деревом, для скаляра — текстовое значение. Подробнее о [разборе Data](./eventlog-data.md). |
| `v8.eventlog.data.presentation` | представление данных |
| `v8.eventlog.server`, `v8.eventlog.port`, `v8.eventlog.sync_port` | рабочий сервер и порты |
| `v8.eventlog.data_separation` | разделители сеанса одной строкой: `<разделитель>=<значение>` через запятую |
| `v8.eventlog.data_separation.<разделитель>` | значение каждого разделителя отдельно; имя разделителя в ключе - транслитом в нижнем регистре, слова через `_` (`ОбластьДанныхОсновныеДанные` → `oblast_dannykh_osnovnye_dannye`), чтобы ключ принимали Loki и Prometheus |
| `log.file.path`, `log.file.name` | путь к файлу журнала и имя файла |
| `v8.eventlog.truncation.attributes` | ключи обрезанных атрибутов, массив строк; без обрезки атрибута нет |
| `v8.eventlog.truncation.body.original_size` | размер тела до обрезки, байт; без обрезки тела атрибута нет |
| `v8.eventlog.truncation.body.attributes` | поля записи, обрезанные в теле, массив строк по порядку тела: `event.presentation`, `metadata`, `data.presentation` (или `data`, если представления данных нет), `user`, `application`, `comment`; только у записи лога, тело которой обрезано внутри полей |

Тело и значения атрибутов ограничены теми же лимитами, что у технологического журнала, см.
[ограничение размеров](./telemetry.md#ограничение-размеров). В `v8.eventlog.data` лимит значения
действует на каждую строку на любой глубине, а в сумму атрибутов входят и вложенные ключи.

Время в журнале регистрации - с точностью до секунды, и платформа пишет в него одинаковые записи
одной секунды. Loki хранит записи одного потока с одинаковыми временем и телом как одну, поэтому
в Loki записей может быть меньше, чем в журнале. Точное количество - метрика `v8.eventlog.records`.

### Метрики

| Метрика | Тип | Атрибуты |
|---------|-----|----------|
| `v8.eventlog.records` | счетчик | `v8.eventlog.event`, `v8.eventlog.severity`, `v8.infobase.name`, `v8.eventlog.application` |
| `v8.eventlog.truncated`, `{value}` | счетчик | `v8.eventlog.event`, `v8.infobase.name`, `v8.eventlog.truncation.target`, `v8.eventlog.truncation.attribute` |
| `v8.eventlog.truncated.size`, `By` | счетчик | те же |

`v8.eventlog.truncated` и `v8.eventlog.truncated.size` - число обрезанных значений и отрезанные байты,
как `v8.techlog.truncated` и `v8.techlog.truncated.size` у технологического журнала.

## Кластер

Показатели кластера снимаются с сервера администрирования `ras` с периодом `interval` его элемента в
`otel.v8-logs.cluster` и отдаются наблюдаемыми датчиками (область инструментирования
`opentelemetry-v8-logs.cluster`): каждый экспорт метрик (`otel.metric.export.interval`) отдает значения
последнего снимка. Все метрики - gauge. Опрашиваются все кластеры агента, кластер различается атрибутом
`v8.cluster.name`; серверы `ras` из массива `otel.v8-logs.cluster` различаются `service.name` ресурса.

### Ресурс

| Атрибут ресурса | Значение |
|-----------------|----------|
| `service.name` | `service-name` элемента `otel.v8-logs.cluster`, по умолчанию `otel.v8-logs.service.name` |
| атрибуты из `otel.v8-logs.resource.attributes` | как заданы |

`v8.infobase.name` в ресурсе метрик кластера нет: один снимок охватывает все базы кластера, и база -
атрибут точки.

### Метрики

| Метрика | Единица | Значение | Атрибуты |
|---------|---------|----------|----------|
| `v8.cluster.up` | - | 1 - последний опрос удался, 0 - нет. При 0 остальные метрики не отдаются; до первого опроса метрик кластера нет | - |
| `v8.cluster.sessions` | `{session}` | число сеансов | `v8.cluster.name`, `v8.infobase.name`, `v8.session.app_id` (приложение сеанса: `1CV8C`, `WebClient`, `BackgroundJob`...), `host.name` рабочего процесса сеанса |
| `v8.cluster.sessions.blocked` | `{session}` | число сеансов, ожидающих блокировку | `v8.cluster.name`, `v8.infobase.name`, `v8.block.kind`: `db` - блокировка СУБД, `lock` - управляемая |
| `v8.cluster.sessions.memory.delta` | `By` | разность выделенной и освобождённой памяти вызовов сеансов; бывает отрицательной | разрез сеансов: `v8.cluster.name`, `v8.infobase.name`, `v8.session.app_id`; окно `v8.window`: `current`, `last5min` |
| `v8.cluster.sessions.cpu_time` | `s` | процессорное время вызовов сеансов | разрез сеансов и `v8.window` |

| `v8.cluster.sessions.call.duration` | `s` | длительность вызовов сеансов | разрез сеансов, `v8.call.kind`: `call` - все вызовы, `db` - вызовы СУБД, и `v8.window` |
| `v8.cluster.sessions.io` | `By` | чтение и запись с диска вызовами сеансов | разрез сеансов, `v8.io.direction`: `read`, `write`, и `v8.window` |
| `v8.cluster.sessions.long_calls` | `{session}` | число сеансов, текущий вызов которых длится не меньше порога | разрез сеансов и `v8.duration.threshold` - порог в секундах (число); точка на каждый порог, в том числе нулевая |
| `v8.cluster.infobase.scheduled_jobs_denied` | - | 1 - регламентные задания базы заблокированы, 0 - нет | `v8.cluster.name`, `v8.infobase.name`; только для баз, учетные данные которых заданы в настройках |
| `v8.cluster.infobase.sessions_denied` | - | 1 - начало сеансов базы заблокировано, 0 - нет | те же |
| `v8.cluster.connections` | `{connection}` | число соединений | `v8.cluster.name`, `v8.infobase.name`, `host.name`, `process.pid`, `v8.connection.app_id` (приложение соединения) |
| `v8.cluster.processes` | `{process}` | число рабочих процессов | `v8.cluster.name`, `host.name`, `v8.process.running`, `v8.process.enabled` (булевы) |
| `v8.cluster.process.memory.usage` | `By` | память рабочего процесса | `v8.cluster.name`, `host.name`, `process.pid` |
| `v8.cluster.process.connections` | `{connection}` | число соединений рабочего процесса | те же |
| `v8.cluster.process.available_performance` | - | доступная производительность рабочего процесса (безразмерная оценка кластера) | те же |
| `v8.cluster.process.call.duration.avg` | `s` | средняя длительность вызовов рабочего процесса | те же и `v8.call.kind`: `call` - вызов, `db` - вызов СУБД, `lock` - ожидание блокировки, `server` - серверный вызов, `back` - обратный вызов |
| `v8.cluster.licenses.used` | `{session}` | число сеансов с лицензией серии | `v8.cluster.name`, `v8.license.series`, `v8.license.server` (адрес менеджера, выдавшего лицензию, - только у лицензий, выданных сервером), `v8.license.type` (числовой код типа лицензии, как его отдает `ras`) |
| `v8.cluster.licenses.total` | `{user}` | число пользователей, допустимое лицензией серии | те же |

В Prometheus (OTLP-экспортер коллектора с суффиксами единиц) метрики получают имена `v8_cluster_sessions`,
`v8_cluster_sessions_memory_delta_bytes`, `v8_cluster_process_call_duration_avg_seconds`,
`v8_cluster_sessions_cpu_time_seconds`: счётные единицы в фигурных скобках и пустая единица суффикса не добавляют.

#### Окна показателей сеансов

Показатели нагрузки сеансов (`memory.delta`, `cpu_time`, `calls`, `call.duration`, `io`) - суммы по сеансам,
существующим на момент снимка, в окне `v8.window`, как его считает кластер:

- `current` - текущий незавершённый вызов сеанса, с его начала; у сеанса без вызова - ноль;
- `last5min` - вызовы, завершённые за последние 5 минут (скользящее окно кластера).

Память - разность выделенной и освобождённой памяти потоками этих вызовов, а не занятая память, поэтому
`memory.delta` бывает отрицательной. Сеансы, завершившиеся внутри окна, в сумму не входят: показатели берутся
только с живых сеансов. Показатели «всего» (с начала сеанса) в метрики не идут - они есть в
[снимках сеансов](#снимки-сеансов). Семантика показателей - «Клиент-серверный вариант. Руководство
администратора», раздел «Операции со списком сеансов»: <https://its.1c.ru/db/v8327doc>.

`host.name` и `process.pid` - рабочий сервер и PID рабочего процесса `rphost`, как их видит кластер;
у соединения и сеанса они берутся от его рабочего процесса. Пустые значения атрибутов не передаются: сеанс без
базы уходит без `v8.infobase.name`, сеанс без рабочего процесса - без `host.name`, лицензия без серии - без
`v8.license.series`.

Пороги долгих вызовов и учетные данные баз задаются в настройках кластера (см. [конфигурацию](./configuration.md)).

### Снимки сеансов

Каждый опрос кластера дает по записи лога на каждый сеанс (область инструментирования
`opentelemetry-v8-logs.cluster`): по ним видно, какой сеанс сколько памяти, времени и ввода-вывода занимал
в момент опроса, - то, чего нет в метриках, атрибуты которых ограничены конечными множествами.
Ресурс записи - `service.name` метрик кластера и `v8.infobase.name` базы сеанса (сеанс без базы - без него),
поэтому в Loki база - индексируемая метка `v8_infobase_name`. Недоступный кластер записей не дает.

| Поле | Значение |
|------|----------|
| Время | момент снимка |
| Тело | `Сеанс <номер> <приложение> <пользователь>`, пустые части пропускаются: `Сеанс 1022 1CV8C Иванов` |
| Серьезность | `INFO` |
| `v8.cluster.name` | имя кластера |
| `v8.infobase.name` | имя информационной базы - в ресурсе записи, не в атрибутах |
| `session.id` | номер сеанса (число); тот же атрибут, что у записей технологического журнала и журнала регистрации, настройка `session-id.enabled` на снимки не действует |
| `v8.session.app_id` | приложение сеанса |
| `user.name` | имя пользователя |
| `host.name`, `process.pid` | рабочий сервер и PID рабочего процесса сеанса |
| `client.address` | компьютер клиента, как у записей технологического журнала и журнала регистрации |
| `v8.session.client.ip` | IP-адрес клиента |
| `v8.session.started_at`, `v8.session.last_active_at` | начало и последняя активность, `yyyy-MM-ddTHH:mm:ss` |
| `v8.session.hibernated` | сеанс спит (булево) |
| `v8.session.blocked.db`, `v8.session.blocked.lock` | номер сеанса, который блокирует этот сеанс: в СУБД и управляемой блокировкой; 0 - не заблокирован |
| `v8.session.memory.current`, `.last5min`, `.total` | память, байты: текущий вызов, за 5 минут, с начала сеанса |
| `v8.session.read.current`, `.last5min`, `.total` | чтение, байты |
| `v8.session.write.current`, `.last5min`, `.total` | запись, байты |
| `v8.session.duration.current`, `.last5min`, `.total` | длительность вызовов, мс |
| `v8.session.duration.dbms.current`, `.last5min`, `.total` | длительность вызовов СУБД, мс |
| `v8.session.cpu_time.current`, `.last5min`, `.total` | процессорное время, мс |
| `v8.session.calls.total`, `.last5min` | число вызовов |
| `v8.session.bytes.total`, `.last5min` | объем данных, переданных между клиентом и сервером, байты |
| `v8.session.dbms_bytes.total`, `.last5min` | объем данных, переданных между сервером и СУБД, байты |
| `v8.session.current_service` | текущий сервис сеанса |
| `v8.session.data_separation` | разделение данных сеанса |
| `v8.session.license.series` | серии лицензий сеанса через запятую |

Числовые атрибуты передаются всегда, строковые - только непустые. Ключи атрибутов - латиницей, в Loki они
становятся структурированными метаданными (`v8_session_memory_current`).

```logql
# память сеанса 1022 базы erp
max_over_time({service_name="<сервис>", v8_infobase_name="erp"} | scope_name="opentelemetry-v8-logs.cluster" | session_id="1022" | unwrap v8_session_memory_current [5m])
# 10 сеансов с наибольшей памятью
topk(10, max by (v8_infobase_name, session_id, user_name) (max_over_time({service_name="<сервис>"} | scope_name="opentelemetry-v8-logs.cluster" | unwrap v8_session_memory_current [5m])))
```

### Связь с трассами технологического журнала

Общие ключи метрик кластера и спанов технологического журнала:

- `v8.infobase.name` - у спанов атрибут ресурса (`p:processName` события), у метрик сеансов и соединений -
  атрибут точки;
- `process.pid` - у спанов PID из имени каталога или файла журнала (`rphost_1234`), у метрик соединений
  и рабочих процессов - PID процесса в кластере;
- `host.name` - у метрик процессов имя рабочего сервера; чтобы он был и у спанов, задайте его в
  `otel.v8-logs.resource.attributes` (`host.name=<имя сервера как в кластере>`) коллектора, читающего журналы
  этого сервера.

Так всплеск `v8.techlog.event.duration` базы или процесса кладется на одну шкалу с числом сеансов, соединений
и памятью того же процесса: метрики и трассы фильтруются одинаковыми значениями `v8_infobase_name`,
`process_pid`, `host_name`.

Идентификаторов сеансов и соединений, пользователей и адресов клиентов в атрибутах метрик нет намеренно:
атрибуты метрик ограничены конечными множествами (кластер, база, приложение, рабочий сервер, процесс,
серия лицензии), у SDK предел 2000 рядов на инструмент. Показатели отдельных сеансов и их пользователи -
в [снимках сеансов](#снимки-сеансов).
